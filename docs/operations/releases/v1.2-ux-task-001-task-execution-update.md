# UX-TASK-001 Task Execution Update Experience

## Existing Architecture Assessment

The Tasks workspace already supports execution edits through the project-scoped task API and `ProjectWorkspaceTasks`. Planning and execution share the same Task aggregate, with planning-only controls gated by component mode and permissions.

## Existing Task Model Review

`Task` already stores status, priority, assignee, percent complete, due date, actual dates, remarks, task kind, hierarchy, and audit actor columns. Priority was read-only in the execution grid because the frontend disabled it outside planning access; no backend or domain constraint prevented priority updates.

## Existing Audit/History Review

The platform has row-level audit columns through `AuditableEntity`. RAID has separate comments/history tables, but Tasks had no task-specific execution timeline. A task-scoped history table was therefore the smallest maintainable addition.

## Recommended Solution

Add `task_execution_updates` inside the existing Tasks domain. The project task workspace records execution updates through a dedicated project-scoped endpoint that delegates to `TasksService`, updates the canonical task, and inserts a history row in one transaction.

## Architecture Impact

No new module was introduced. The implementation reuses Tasks and Projects services, existing task permissions, existing project member validation, existing priority values, and the existing project workspace component.

## Database Impact

Migration `034_ux_task_001_task_execution_updates.sql` creates `task_execution_updates` with task/project references, execution fields, change metadata, audit fields, and reporting-oriented indexes by task, project, owner, and target completion date.

## API And Backend Changes

- `POST /projects/:projectId/tasks/:taskId/execution-updates`
- `TasksService.recordExecutionUpdate(...)`
- Latest execution update is attached to task responses where project tasks are loaded.

## Frontend Implementation

The execution-mode Tasks grid now shows a lightweight `Update` action per non-summary task. It opens a right-hand drawer with status, priority, progress, assignee, next step, next action owner, target completion date, and update notes.

## Validation Rules

Progress must be 0 to 100. Priority must be one of `low`, `medium`, `high`, or `critical`. Assignee and next action owner must be project members when provided. Summary tasks cannot receive execution updates.

## Audit/History Integration

Each execution update records current execution state, changed field values, updated by, and updated on. The canonical task is updated so the grid shows latest status, priority, progress, assignee, due date, and remarks.

## Automated Tests

- Backend service tests cover task execution history creation and existing project task behavior.
- Frontend component tests cover the execution update drawer payload.
- API client tests cover the new endpoint contract.

## Manual Verification Checklist

1. Open a project Tasks workspace.
2. Select `Update` for a standard task.
3. Change status, priority, progress, assignee, next step, next action owner, target completion date, and notes.
4. Save the update.
5. Confirm the drawer closes and the grid reflects status, priority, progress, assignee, target date, and notes.
6. Confirm the database contains a `task_execution_updates` row with audit metadata.
