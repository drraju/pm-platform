# v1.0.5.9.2 Platform Hardening

Date: 2026-06-13

## Summary

v1.0.5.9.2 hardens the PM Platform in three areas that were still fragile after the earlier UI and authorization releases:

- long-form modal usability
- deployment startup and dependency validation
- RAID auditability and soft-delete traceability

## Root Causes Addressed

1. Modal behavior was only partially standardized. The shared shell existed, but task, project, and RAID forms still relied on screen-specific structure, which made long forms harder to maintain and more likely to regress.
2. Deployment startup had no built-in migration runner, no dependency readiness validation, and no health endpoints for container orchestration. This made deployments vulnerable to partial startup and silent boot failures.
3. RAID items supported basic CRUD but lacked an audit trail for comments, owner/status changes, and soft-delete attribution.

## What Changed

### 1. Modal Framework Hardening

Added a reusable modal form composition layer on top of the shared `AppModal` shell:

- sticky header
- sticky footer
- `max-height: 90vh`
- scrollable body
- responsive form sections and grids

Applied to:

- Create Task
- Edit Task
- Reassign Task
- Project create/edit form
- RAID create/edit form

### 2. Deployment Hardening

Added backend startup preparation with:

- required environment validation
- automatic SQL migration execution
- migration status logging
- dependency readiness validation for PostgreSQL and Redis
- fail-fast startup before the API begins listening

Added health checks for:

- PostgreSQL in `docker-compose.yml`
- Redis in `docker-compose.yml`
- Backend via `GET /health`
- Frontend via `GET /api/health`

Docker images now expose container `HEALTHCHECK`s for backend and frontend.

### 3. RAID Auditability

Added:

- `raid_comments` table and API support
- `raid_history_entries` table and API support
- status change history
- owner change history
- general field update history
- comment history events
- soft-delete history events
- `deleted_by_id` population during soft delete

RAID responses now include embedded comments and history so the UI can show the audit trail inside the edit modal.

## Audit Model

### RAID Comments

- Stored in `raid_comments`
- Linked by `raid_item_id`, `raid_type`, and `project_id`
- Captures author, body, timestamps, and audit columns

### RAID History

- Stored in `raid_history_entries`
- Tracks:
  - `created`
  - `updated`
  - `status_changed`
  - `owner_changed`
  - `commented`
  - `deleted`
- Captures actor, field name, previous value, next value, optional JSON change payload, timestamps, and audit columns

### RAID Delete Model

- RAID deletes are soft deletes
- `deleted_at` is set by the ORM soft-delete path
- `deleted_by_id` is now explicitly recorded before soft removal

## Deployment Improvements

- Containers now expose machine-readable health endpoints.
- Docker Compose waits for healthy PostgreSQL and Redis before backend startup.
- Frontend waits for a healthy backend container.
- The backend now fails startup early when critical environment variables or dependencies are missing.
- Pending SQL migrations run automatically during startup and are tracked in `schema_migrations`.

## Remaining Technical Debt

- Existing SQL migrations are auto-run and tracked from this release forward, but older environments that applied SQL manually still rely on the idempotency of those historical scripts rather than a pre-existing migration ledger.
- RAID comments and history are embedded into RAID item responses, which is acceptable for current scale but may eventually need pagination if audit volume grows significantly.
- Health checks currently validate Redis by TCP connectivity rather than a full protocol-level command exchange.
- Backend root route still returns the legacy hello-world payload and has not yet been aligned to platform metadata conventions.
