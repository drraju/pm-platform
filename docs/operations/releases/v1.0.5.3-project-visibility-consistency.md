# v1.0.5.3 Project Visibility and Assignment Consistency

Date: 2026-06-12

## Executive Summary

v1.0.5.3 centralizes project visibility so project lists, workspaces,
dashboards, portfolio summaries, and task reads use one consistent model. Scoped
roles no longer receive unrelated projects, and dashboard assigned-project counts
now include projects where the user has assigned tasks even if membership data is
missing.

## Root Cause

Project visibility was implemented independently across services:

- `GET /projects` returned all projects.
- Portfolio summary aggregated all projects, risks, issues, and tasks.
- Dashboard assigned-project counts were based on ownership and membership, but
  not task assignment.
- `/tasks` returned all tasks regardless of the caller's visible project set.

This caused Customer, Partner, and Team Member users to see unrelated projects,
and caused dashboard project counts to disagree with My Tasks.

## Visibility Matrix

| Role | Project Visibility |
| --- | --- |
| `SUPER_ADMIN` | All projects |
| `Admin` | All projects |
| `Program Manager` | All projects |
| `Portfolio Manager` | All projects |
| `Executive` | All projects, read-only by permissions |
| `Project Manager` | Projects owned by the user, project memberships, and projects with assigned tasks |
| `Delivery Lead` | Projects owned by the user, project memberships, and projects with assigned tasks |
| `Team Member` | Project memberships and projects with assigned tasks |
| `Partner` | Assigned projects through membership or task assignment |
| `Customer` | Assigned projects through membership or task assignment |

## API Changes

The following APIs now use centralized project visibility:

| API | Behavior |
| --- | --- |
| `GET /projects` | Returns only visible projects for scoped roles; all projects for all-project roles |
| `GET /projects/:id` | Requires the project to be visible to the caller |
| `GET /projects/:id/members` | Requires the project to be visible to the caller |
| `GET /projects/:projectId/tasks` | Requires the project to be visible to the caller |
| `GET /projects/:id/risks` | Requires the project to be visible to the caller |
| `GET /projects/:id/issues` | Requires the project to be visible to the caller |
| `GET /projects/:id/assumptions` | Requires the project to be visible to the caller |
| `GET /projects/:id/dependencies` | Requires the project to be visible to the caller |
| `GET /portfolio/summary` | Aggregates only visible projects and related risks, issues, and tasks |
| `GET /dashboard/me` | Assigned projects come from the same visible project model |
| `GET /tasks` | Returns tasks only from visible projects |
| `GET /tasks/:id` | Hides tasks from non-visible projects |

`GET /tasks/my` remains assigned-user scoped and continues to return the user's
own tasks.

## Implementation Notes

New service:

- `backend/src/modules/projects/project-visibility.service.ts`

Core methods:

- `getVisibleProjects(actor)`
- `getVisibleProjectIds(actor)`
- `canViewProject(projectId, actor)`

The visibility service treats task assignment as a project visibility signal for
scoped roles. This fixes the dashboard consistency issue where assigned tasks
existed but assigned project count was zero.

## Security Considerations

- Project IDs hidden from scoped roles are removed from list APIs and task list
  APIs.
- Single project/task reads now deny access when the project is outside the
  caller's visible project set.
- Executive users can see all projects through visibility but remain read-only
  through existing task/team/project mutation permissions.
- The centralized service avoids future drift between dashboard, portfolio,
  project workspace, and task views.

## Remaining Gaps Before v1.0.6

- RAID global list APIs still need the same project visibility filtering if they
  remain available outside project workspaces.
- Risk-only APIs should be reviewed for project visibility alignment.
- Read endpoints should add explicit `project.read`, `portfolio.view`, or
  dashboard read permission decorators where they currently rely on JWT plus
  service filtering.
- Database-backed e2e tests should verify seeded-role JWT behavior against a real
  PostgreSQL test database.
