# v1.0.5.2 Authorization Hardening

Date: 2026-06-12

## Executive Summary

v1.0.5.2 removes the project workflow dependency on the administrative
`GET /users` endpoint. Project assignment and team-management screens now use
`GET /users/assignable` or project-scoped member data, allowing Program
Managers, Project Managers, and Delivery Leads to perform project operations
without receiving `user.manage`.

## Root Cause

The Projects and Project Workspace UI loaded all users through `GET /users`.
That endpoint is correctly protected by `user.manage`, so non-admin delivery
roles received `403 Forbidden` before task assignment or team management could
render. A temporary testing workaround granted `user.manage` to Program Manager,
which widened administrative access beyond normal project workflows.

## API Changes

| API | Purpose | Authorization |
| --- | --- | --- |
| `GET /users/assignable` | Returns active users eligible for project ownership, task assignment, and team membership selectors. | `project.read` OR `project.team.manage` |
| `GET /projects/:projectId/members` | Returns project members with project role and organisation role. | `project.read` OR `project.team.manage` |
| `GET /users` | Administrative user list. Preserved unchanged. | `user.manage` |

`GET /users/assignable` response:

```json
[
  {
    "id": "user-id",
    "email": "jane.doe@example.com",
    "firstName": "Jane",
    "lastName": "Doe",
    "displayName": "Jane Doe",
    "role": "Project Manager"
  }
]
```

`GET /projects/:projectId/members` now includes:

- `user.id`
- `user.displayName`
- `role` as the project membership role
- `user.role` as the organisation role name

## Authorization Model

| Role | Project Workflows | User Administration |
| --- | --- | --- |
| Admin | Full access through permissions | Allowed |
| SUPER_ADMIN | Full access through bypass | Allowed |
| Program Manager | Create, edit, delete, reassign tasks; manage team | Not allowed unless explicitly granted |
| Project Manager | Create, edit, delete, reassign tasks; manage team | Not allowed unless explicitly granted |
| Delivery Lead | Team and task management based on assigned project rules | Not allowed unless explicitly granted |
| Team Member | Update assigned tasks, remarks, percent complete, status, and reassignment within team rules | Not allowed |
| Executive | Read-only project and reporting access | Not allowed |
| Customer | Read-oriented project access | Not allowed |
| Partner | Assigned contributor access | Not allowed |

The backend now supports `@RequireAnyPermissions(...)` for endpoints that accept
one of several permissions. Existing `@RequirePermissions(...)` behavior remains
an all-permissions check.

## Migration Steps

Migration:

- `backend/src/database/migrations/004_v1_0_5_2_authorization_hardening.sql`

Actions:

- Deletes `user.manage` grants from non-admin delivery/stakeholder roles.
- Preserves `user.manage` for `Admin` and `SUPER_ADMIN`.
- Leaves the `user.manage` permission key in place for administrative screens.

## Frontend Changes

Project workflow screens no longer call `GET /users`:

- `frontend/app/(app)/projects/page.tsx`
- `frontend/app/(app)/projects/[id]/page.tsx`
- `frontend/app/(app)/raid/page.tsx`

Admin user management remains the only normal frontend `getUsers()` consumer:

- `frontend/app/(app)/users/page.tsx`

## Remaining Authorization Gaps

- Project list/detail read endpoints still rely primarily on JWT plus downstream
  service rules in several areas; a future release should consistently annotate
  read endpoints with `project.read`, `raid.read`, or portfolio-specific keys.
- Delivery Lead project scope is still enforced by service/project membership
  checks, not by a separate `task.update.assigned-project` permission key.
- Frontend route hiding is permission-driven, but direct route access still
  depends on backend API authorization for final enforcement.

## Recommendations Before v1.0.6

- Add database-backed authorization e2e tests that create users/roles and verify
  real JWT access for each role.
- Introduce separate own-task permissions such as `task.update.own` if Team
  Member and Partner capabilities need finer-grained UI controls.
- Add route-level read permission decorators across read-only controllers for a
  uniform authorization contract.
