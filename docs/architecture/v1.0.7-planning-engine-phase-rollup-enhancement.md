# v1.0.7 Planning Engine Phase Rollup Enhancement

## Summary

Version `v1.0.7` keeps the existing database representation of a phase as
`task_kind = summary`, but changes application behavior so summary rows behave
like enterprise planning phases rather than assignable work items.

No schema or migration changes are required.

## Service-Layer Model

The enhancement is implemented as a service-layer decoration pass in
`backend/src/modules/tasks/planning-rollup.ts`.

That module is responsible for:

- Classifying plan items as phases, tasks, or milestones.
- Calculating phase progress from descendant standard tasks only.
- Rolling phase planned dates up from descendant non-phase plan items.
- Returning separate phase/task/milestone counters.
- Preserving backward compatibility by leaving persisted rows unchanged.

## Rollup Rules

### Progress

For every `task_kind = summary` row:

- Descendant standard tasks are collected recursively.
- Phase progress is calculated as:

  `sum(descendant task percentComplete) / total descendant standard tasks`

- The result is exposed as `phaseProgress`.
- `percentComplete` is decorated in API responses to match the calculated value.
- The value is never persisted back to the database for phase rows.
- Status and progress are normalized for work tasks: `status = done` sets
  `percentComplete = 100`, and `percentComplete = 100` sets `status = done`.

### Dates

For every phase:

- `phaseStartDate` is the earliest descendant planned start date.
- `phaseEndDate` is the latest descendant planned finish date.
- If no descendant dated work exists, the phase falls back to its manually
  entered planned dates.

## Guardrails

Task and project task mutations now block summary-task behavior that conflicts
with phase semantics:

- Phases cannot be assigned.
- Phases cannot accept manual status updates.
- Phases cannot accept manual percent-complete updates.
- Phases cannot store effort values.

These rules are enforced in both `TasksService` and `ProjectsService` so the
standalone task API and project workspace API stay aligned.

## API Additions

Project workspace task responses now expose calculated planning fields:

- `phaseProgress`
- `phaseStartDate`
- `phaseEndDate`
- `childTaskCount`

Project payloads also expose calculated counters:

- `taskCounts.phases`
- `taskCounts.tasks`
- `taskCounts.milestones`

## UI Behavior

The project workspace plan tab now:

- Labels summary rows as phases.
- Displays `[PHASE]`, `[TASK]`, and `[MILESTONE]` badges.
- Uses calculated phase progress and rolled-up dates in the grid.
- Hides assignee, status, and effort controls for phases.
- Shows read-only calculated phase fields during editing.
- Separates phase, task, and milestone counts in the workspace summary.

## Compatibility Notes

- Existing projects continue to work with `task_kind = summary`.
- Persisted summary-task values are not migrated or rewritten.
- Any legacy summary-task assignment or manual progress data is ignored by the
  decorated API response and blocked on future edits.
