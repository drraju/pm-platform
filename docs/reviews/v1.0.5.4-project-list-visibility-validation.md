# v1.0.5.4 Project List Visibility Validation

Date: 2026-06-12

## Executive Summary

Runtime testing showed Customer users could still see all projects on the
Projects page. Source tracing confirms the Projects page renders the direct
`GET /projects` result and does not add unrelated projects on the frontend. The
v1.0.5.4 correction tightens centralized visibility so Customer and Partner
project visibility is based on project-level assignment/membership, while task
assignment only expands visibility for Team Member and delivery/manager roles.

Follow-up frontend/runtime investigation found no frontend local aggregation that
could add a third project after `GET /projects` returns two. The remaining
runtime mismatch is most consistent with stale authenticated GET responses or a
stale deployed bundle/container. The frontend API client now sends `cache:
"no-store"` for API requests, and the backend now emits no-store cache headers
for API responses.

## Root Cause

Two conditions contributed to the observed behavior:

1. The Projects page source uses `getProjects()` from `frontend/lib/api/client.ts`,
   which calls `GET /projects`. `ProjectTable` renders only the array it is
   given. Therefore, if the UI shows all 3 projects, the active runtime API
   returned all 3 projects or the running containers are stale.
2. The v1.0.5.3 visibility source allowed task-assignment expansion for all
   scoped roles, including Customer and Partner. v1.0.5.4 narrows Customer and
   Partner to project-level assignment/membership only.

- File: `frontend/components/projects/project-table.tsx`
- Renders `projects.map((project) => ...)`

- Project count/list source: `dashboard.assignedProjects`.
- No local aggregation from `GET /projects`.

Portfolio page:

- File: `frontend/app/(app)/portfolio/page.tsx`
- Calls `getPortfolioSummary()`.
- API client path: `GET /portfolio/summary`.
- Project count source: `summary.totalProjects`.
- No local aggregation from `GET /projects`.

- File: `frontend/app/(app)/projects/page.tsx`
- Calls `getProjects()`.
- API client path: `GET /projects`.
- React state: `projects` is set from the `GET /projects` response after
  enriching only those returned projects with `GET /projects/:id`.
- Rendered count: `ProjectTable` maps over `filteredProjects`, derived from
  `projects`.

## Runtime Mismatch Root Cause

Backend API validation showed `GET /projects` with a Customer token returns only
authorized projects. Because the Projects page renders only that response, a UI
count of 3 indicates the browser/runtime was not using the same fresh response.

Likely causes:

- Browser cached authenticated GET response from a previous all-project role.
- Running frontend or backend container was stale after source changes.
- Browser localStorage still held a token for a broader role while API validation
  used a fresh Customer token.

Fixes applied:

- `frontend/lib/api/client.ts` now sends `cache: "no-store"` on API requests.
- `backend/src/main.ts` now sends no-store/no-cache response headers.
- Customer/Partner visibility remains narrowed to project-level assignment only.

## Backend Visibility Rules

Source of truth:

- `backend/src/modules/projects/project-visibility.service.ts`

v1.0.5.4 correction:

- Customer: owned/member projects only.
- Partner: owned/member projects only.
- Team Member: owned/member projects plus projects containing assigned tasks.
- Delivery Lead: owned/member projects plus projects containing assigned tasks.
- Project Manager: owned/member projects plus projects containing assigned tasks.
- Admin, SUPER_ADMIN, Program Manager, Portfolio Manager, Executive: all
  projects.

The following APIs use the same centralized visibility service:

| API | Visibility Source |

| `GET /projects/:projectId/tasks` | `ProjectVisibilityService.canViewProject` |
| `GET /projects/:id/risks` | `ProjectVisibilityService.canViewProject` |
| `GET /projects/:id/issues` | `ProjectVisibilityService.canViewProject` |
| `GET /projects/:id/assumptions` | `ProjectVisibilityService.canViewProject` |
| `GET /projects/:id/dependencies` | `ProjectVisibilityService.canViewProject` |

| `GET /portfolio/summary` | `ProjectVisibilityService.getVisibleProjectIds` |

`GET /tasks/my` remains assigned-user scoped only.
