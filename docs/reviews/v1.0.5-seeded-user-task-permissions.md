# v1.0.5 Seeded User Task Permission Investigation

Date: 2026-06-12
Scope: Live seeded users, project membership roles, frontend task/team visibility, and backend task/team permission grants.

## Data Sources

- Live Docker database: `pm-platform-postgres-1`, database `pm_platform`.
- Current frontend source: `frontend/app/(app)/projects/[id]/page.tsx`.
- Current backend source: `backend/src/modules/projects/projects.controller.ts`, `backend/src/modules/tasks/tasks.controller.ts`, `backend/src/common/authz/permissions.ts`.
- Running backend container bundle: `pm-platform-backend-1`.

## Key Findings

The live database and current repository source are out of sync.

- The live database has legacy colon-style permission keys such as `project-tasks:create`, `project-tasks:update:any`, and `project-members:manage`.
- Current backend source requires v1.0.5 dot-style keys such as `task.create`, `task.update`, `task.delete`, and `project.team.manage`.
- The running backend container is stale relative to current source. Its compiled task/project task routes use `JwtAuthGuard` only and do not include `PermissionsGuard` or pass `request.user` into the service-level task/team authorization checks.
- Current frontend source does not read backend permissions. It shows controls only for exact role names `Program Manager` or `Project Manager`, or project membership roles `owner` / `manager`, excluding `Executive`.

## Frontend Visibility Rule

Current frontend source computes Project Workspace task/team management as:

```ts
const roleName = currentUser?.role?.name ?? "";
const hasGlobalTaskManagement =
  roleName === "Program Manager" || roleName === "Project Manager";
const hasProjectManagement =
  currentMembership?.role === "owner" || currentMembership?.role === "manager";
const isExecutive = roleName === "Executive";
const canManageTasks =
  !isExecutive && (hasGlobalTaskManagement || hasProjectManagement);
const canManageTeam = canManageTasks;
```

Evidence: `frontend/app/(app)/projects/[id]/page.tsx:493`.

## Backend Permission Definitions Used In This Report

Because the live system has multiple mismatched layers, the table below uses these definitions:

- **Can Manage Tasks (Frontend)**: Current frontend visibility check.
- **Can Manage Tasks (Backend)**: Live database RBAC grant using legacy permissions. `Yes` means the role has `project-tasks:create`, `project-tasks:update:any`, and `project-tasks:delete`. `Partial` means broad create/update exists but delete is missing. `Own only` means only own-task update is granted.
- **Can Manage Team (Frontend)**: Same current frontend check as task management.
- **Can Manage Team (Backend)**: Live database RBAC grant for `project-members:manage`.

Important runtime caveat: the currently running backend container appears stale and does not enforce these RBAC grants on task/team write routes. If current repository backend source is rebuilt against the current live database without applying v1.0.5 dot-style permission migrations, protected writes would fail because the required dot-style permission keys are absent.

## Runtime Deployment Findings

The running backend container is not aligned with the current repository source:

- Running compiled `TasksController` uses only `JwtAuthGuard`; current source uses `JwtAuthGuard` and `PermissionsGuard`.
- Running compiled task create/update/delete handlers do not pass `request.user` into service methods; current source does.
- Running compiled Project task/member handlers do not include `RequirePermissions`; current source does.

This means the live container may allow operations that current source would block. After rebuilding the backend from current source, the live database must also contain the v1.0.5 dot-style permissions or task/team write APIs will fail permission checks.

## Evidence

Live seeded users and memberships were verified with:

```sql
SELECT u.email, r.name AS role_name, p.name AS project_name, pm.role AS project_role
FROM users u
JOIN roles r ON r.id = u.role_id
LEFT JOIN project_members pm ON pm.user_id = u.id
LEFT JOIN projects p ON p.id = pm.project_id
ORDER BY u.email, p.name;
```

Live role permissions were verified with:

```sql
SELECT r.name AS role_name, string_agg(perm.key, ', ' ORDER BY perm.key) AS permissions
FROM roles r
LEFT JOIN role_permissions rp ON rp.role_id = r.id
LEFT JOIN permissions perm ON perm.id = rp.permission_id
GROUP BY r.name
ORDER BY r.name;
```

The live `permissions` table contains legacy keys only; it does not contain `task.create`, `task.update`, `task.delete`, `task.reassign`, `task.comment`, or `project.team.manage`.
