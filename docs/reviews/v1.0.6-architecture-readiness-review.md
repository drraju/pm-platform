# v1.0.6 Architecture Readiness Review

Review date: 2026-06-13

## Executive Summary

The platform has a solid MVP core for authentication, RBAC-backed roles, project workspaces, project team management, task operations, RAID capture, portfolio summary, and a working frontend shell. The repo is also in a healthy delivery state today: backend tests, frontend tests, backend build, and frontend build all passed during this review.

The architecture is not yet ready for a broad "planning/Gantt/resource management" expansion without some targeted refactoring. The current model is still strongly project-centric, authorization rules are split across permissions, role names, and membership heuristics, and the task model lacks the scheduling structures required for serious planning. `v1.0.6` should proceed only as a task planning foundation release, not as a full planning feature release.

## Highest-Risk Findings

### 1. Project mutation endpoints are insufficiently protected

`POST /projects`, `PATCH /projects/:id`, and `DELETE /projects/:id` do not require explicit project permissions in the controller, and the service methods do not receive or validate the acting user. That means project mutation rules are materially weaker than task/team mutation rules.

Impact:

- Weakens enterprise trust in RBAC boundaries.
- Makes future customer/partner visibility harder to harden.
- Creates inconsistency between documented permissions and actual enforcement.

### 2. Manager authorization relies on role-name heuristics instead of stable policy checks

Both `ProjectsService` and `TasksService` decide elevated access using hardcoded role-name sets and a lookup that queries `users` by `roleId`, then inspects the joined role name. This is an indirect proxy for actor capability rather than a direct policy decision.

Impact:

- Role renames become risky.
- Permission grants and actual behavior can diverge.
- Future introduction of program, portfolio, partner, and customer variants becomes harder.

### 3. RAID authorization is internally inconsistent and deletion bypasses soft-delete conventions

`RaidService.ensureCanUpdateItem()` grants update access to roles with `raid.delete`, and also restricts `raid.update` to item owners only. Separately, RAID removal uses `repository.remove()` while the core entities support `deleted_at`, unlike projects and tasks which use soft delete.

Impact:

- RAID behavior is harder to reason about than task/project behavior.
- Auditability is weaker for a PMO-critical register.
- Enterprise governance workflows will struggle without reliable lifecycle history.

### 4. The data model is not yet ready for enterprise planning features

Tasks have useful MVP fields such as planned and actual dates, but there are no task dependencies, milestones, work estimates, sprint/iteration buckets, baselines, resource assignments, or cross-project planning structures. The domain also has no first-class `program`, `portfolio`, `workstream`, or `project hierarchy` entities.

Evidence:

- [backend/src/modules/tasks/entities/task.entity.ts](/Users/ramdatla/Projects/pm-platform/backend/src/modules/tasks/entities/task.entity.ts:1)

Impact:

- Gantt/timeline features would become UI overlays on incomplete data.
- Cross-project dependency management cannot be modeled cleanly.
- Resource planning would require schema changes after feature work has already started.

### 5. Deployment and migration flow is still MVP-grade

Docker Compose mounts only the initial schema into Postgres bootstrap. The SQL migrations in `backend/src/database/migrations` are not automatically executed, and there are no health checks or orchestration readiness gates in Compose.

Evidence:

- v1.0.6 schema changes will be harder to deploy safely.
- Recovery and rollback discipline is not yet where an enterprise PM platform should be.

## Area-by-Area Assessment

### 1. Database Architecture

Strengths:

- Core entities are normalized reasonably for MVP scope.
- `project_members` is the right join table shape for project-level participation.
- `tasks`, `risks`, `issues`, `assumptions`, and `dependencies` all anchor to `project_id`.
- Audit columns and soft-delete support exist in the shared base entities.

Weaknesses:

- No first-class model for portfolios, programs, workstreams, or project hierarchies.
- RAID is split across four tables, which is workable now but makes unified workflow, reporting, and configurable metadata harder later.
- `dependencies.depends_on` is free text rather than a relational dependency edge.
- No task dependency table, milestone table, estimate model, capacity model, calendar model, or baseline model.
- Project ownership and project membership are separate concepts but not fully unified as a governance model.

Missing entities recommended before or during v1.0.6:

- `portfolios`
- `programs`
- `program_projects` or `project_program_membership`
- `task_dependencies`
- `milestones`
- `project_phases` or `plan_buckets`
- `resource_assignments`
- `task_estimates`
- `project_status_history`
- `raid_comments` and `raid_history`

Migration concerns:

- Additive migrations are safe, but any later effort to retrofit dependencies, portfolio hierarchy, or resource planning into current tables will become progressively more expensive.
- v1.0.6 is the right point to add new planning tables before timeline UI hardens around the current task shape.

### 2. Authorization Architecture

Strengths:

- Permission entities, role entities, role-permission mapping, and a reusable `PermissionsGuard` are in place.
- `GET /auth/me` returns effective user, role, and permission data, which is useful for frontend shaping.
- Project visibility is centralized in one service instead of spread across controllers.

Weaknesses:

- Enforcement is uneven across modules.
- Visibility is partly permission-driven, partly role-name-driven, and partly membership-driven.
- Customer/Partner boundaries are visibility-only today; there is no stronger tenant or classification boundary.
- Frontend still derives navigation and action affordances from locally stored permission state.

Simplification opportunities:

- Convert role-name logic into capability/policy logic.
- Make project visibility an explicit policy object with reusable decision methods.
- Separate `canViewProject`, `canManageProject`, `canManageTask`, and `canManageRaid` into a single authorization service layer.

### 3. Project Management Model

Current quality:

- Good for single-project execution.
- Adequate for team membership and project workspace delivery.
- Not yet adequate for program governance.

Readiness:

- Programs: not ready
- Portfolios: partially ready for reporting only
- Cross-project dependencies: not ready
- Ownership/governance: partially ready

Recommended changes:

- Add first-class program and portfolio entities.
- Add project hierarchy and grouping support.
- Add project sponsor, delivery lead, and business owner fields as distinct governance roles.
- Add project category, lifecycle stage, and reporting cadence metadata.

### 4. Task Architecture

Current quality:

- Good MVP execution model.
- Strong enough for task CRUD, assignment, percent complete, and simple dashboarding.
- Not yet a planning model.

Readiness:

- Planning: partial
- Timeline: partial
- Gantt: not ready
- Resource planning: not ready

Schema changes recommended before v1.0.6:

- Add `task_dependencies` table with dependency type and lag.
- Add `is_milestone` and optionally a separate `milestones` table.
- Add `sequence` or ordering fields for board/timeline stability.
- Add `estimate_hours`, `remaining_hours`, and `effort_points`.
- Add `baseline_start_date` and `baseline_end_date`.
- Add `parent_task_id` for hierarchy.
- Add `workstream_id` or `phase_id`.

### 5. RAID Architecture

Strengths:

- Core RAID categories are present.
- Ownership, status, and category-specific fields exist.
- The frontend RAID management surface is already reusable.

Weaknesses:

- Workflow maturity is limited.
- No comments, history, escalation, review cadence, or approval model.
- Dependencies are not relational and therefore cannot support enterprise dependency tracing.
- RAID lifecycle rules are less consistent than task lifecycle rules.

Enterprise suitability:

- Suitable for MVP delivery teams.
- Not yet suitable for PMO-grade governance without history, commentary, approval, and reporting enrichment.

### 6. API Architecture

Strengths:

- NestJS module structure is clear.
- DTO usage is generally good.
- Endpoint naming is understandable.

Weaknesses:

- Service layer mixes orchestration, authorization, and repository concerns.
- API structure is still resource-centric rather than use-case-centric.
- Missing pagination, filtering standards, and versioning strategy.
- Shell modules exist for notifications and integrations but are not yet real API surfaces.

Refactoring opportunities:

- Introduce application services/use cases for project planning, RAID governance, and portfolio reporting.
- Add common paginated list DTOs and query conventions.
- Normalize mutation permission checks across all modules.

### 7. Frontend Architecture

Strengths:

- Reusable layout, modal, workspace, table, and RAID components exist.
- Workspace UI composition is strong for current scope.
- Tests cover key user workflows well.

Weaknesses:

- Session and permission state are stored in `localStorage`, including refresh token material.
- Many pages reload their own auth/profile context independently.
- Data fetching and mutation state are manual and repeated rather than centralized.
- UI permissions remain partially client-derived.

Evidence:

### 8. Enterprise PM Capability Gaps

Compared with Microsoft Project, Monday.com, ClickUp, Jira, and Planview, the biggest missing capabilities are:

- program hierarchy
- portfolio governance
- planning baselines
- task dependencies
- milestones
- resource capacity planning
- calendar and availability modeling
- scenario planning
- status history and trend reporting
- PMO-grade RAID workflow
- executive analytics beyond current summary cards

### 9. Readiness Assessment

Ready for `v1.0.6 Task Planning Foundation`:

- Yes, conditionally

Not ready for:

- full timeline/Gantt delivery
- resource planning
- PMO-grade portfolio management
- program-level dependency management

## Strengths

- Good MVP domain coverage across projects, tasks, RAID, dashboard, and portfolio.
- Healthy test/build baseline.
- Reusable frontend workspace and modal patterns.
- Reasonable normalized relational model for current single-project scope.
- Clear opportunity to extend instead of rewrite.

## Risks

- Authorization drift as new roles and planning workflows are added.
- Schema debt if timeline/Gantt is built before dependency and baseline tables exist.
- Weak deployment discipline for additive schema evolution.
- Customer/Partner isolation remains policy-based rather than hard boundary-based.

## Technical Debt

- services are doing domain logic, authorization, and persistence orchestration together
- role-name checks are embedded in business logic
- migrations are not part of runtime deployment flow
- integrations and notifications are still skeletal
- frontend session and permission handling is repeated and client-heavy

## Recommended Refactoring Before v1.0.6 Feature Expansion

1. Harden project mutation authorization and align controller/service checks to permission policy.
2. Replace role-name heuristics with centralized authorization policies.
3. Fix RAID update/delete authorization semantics and move RAID deletion to soft delete.
4. Introduce planning schema additions before timeline UI work.
5. Add migration execution and service health checks to deployment flow.
6. Create a shared frontend session/data access layer.

## Recommended v1.0.6 Approach

Treat `v1.0.6` as a foundation release with three tracks:

1. Authorization hardening
2. Planning schema foundation
3. Thin planning UI

Scope recommendation:

- add task dependencies, milestone support, task hierarchy, and baseline dates
- add project planning API endpoints
- add a simple project timeline data service
- keep UI to planning forms and read-only timeline scaffolding
- defer full drag/drop Gantt, resource heatmaps, and scenario planning

## Priority-Ranked Recommendations

1. Fix project mutation authorization before adding new planning endpoints.
2. Add task dependency and milestone schema before building Gantt UI.
3. Centralize policy decisions for project/task/RAID authorization.
4. Add migration execution to Docker/runtime flow.
5. Add program and portfolio domain entities before cross-project planning.
6. Refactor frontend session/data fetching into shared providers/hooks.
7. Expand RAID into comments, history, and governance workflow.
8. Build resource planning only after dependency and hierarchy data exists.

## Architecture Score

6.2 / 10

Rationale:

- strong MVP foundation
- healthy engineering baseline
- meaningful domain coverage
- but still too project-centric and policy-fragmented for enterprise planning without targeted refactoring

## Go / No-Go Recommendation

Go for `v1.0.6` only if the release is explicitly scoped as `Task Planning Foundation`.

No-Go for a broader `v1.0.6` that attempts to deliver full planning, Gantt, resource management, or PMO-grade portfolio capabilities on the current architecture without the refactors above.
