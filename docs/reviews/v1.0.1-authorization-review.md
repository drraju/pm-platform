# v1.0.1 Authorization Hardening Review

Review date: 2026-06-07

## Review Scope

This review covers authorization for:

- Executive Dashboard
- Portfolio Dashboard
- Project Workspace
- My Tasks
- Dashboard
- Risks
- Issues
- Assumptions
- Dependencies

The review is documentation-only and is based on repository inspection of backend controllers/services, auth guards, entities, frontend navigation, and app routes.

## Current Authorization Model

### Backend

The current backend authorization model is authentication-only for the reviewed application areas.

- Protected controllers use `@UseGuards(JwtAuthGuard)`.
- `JwtAuthGuard` extends Passport `AuthGuard('jwt')`.
- `JwtStrategy` validates the JWT and attaches `{ userId, email, roleId }` to the request.
- Roles, permissions, and role-permission relationships exist as entities and database tables.
- No `RolesGuard`, `PermissionsGuard`, project membership guard, ownership guard, policy guard, or decorator such as `@Roles()` or `@RequirePermissions()` is currently applied to the reviewed endpoints.
- Project membership validation exists for task assignee correctness, but not for caller authorization.

### Frontend

The frontend has no visible route-level permission model.

- The application shell shows Dashboard, Executive, Portfolio, Projects, My Tasks, Risks, Issues, and Notifications to every authenticated user.
- Frontend route visibility is not based on role, permission, project membership, ownership, or project role.
- Some screens check whether a token exists before enabling actions, but they do not check whether the authenticated user is allowed to perform the action.
- Frontend access control should be treated as user experience only. Backend guards must enforce all security decisions.

## Missing Authorization Guards

### Required Guard Types

- `RolesGuard`: allows endpoints based on user role names or role ids.
- `PermissionsGuard`: allows endpoints based on permission keys attached to the user's role.
- `ProjectAccessGuard`: verifies the user is project owner, project member, or has a portfolio/global permission.
- `ProjectRoleGuard`: verifies the user has an allowed project role for project-level mutations.
- `ResourceOwnerGuard` or policy handler: verifies ownership for task, risk, issue, assumption, dependency, and notification records.
- `ActiveUserGuard`: blocks inactive, suspended, or deleted users after JWT validation.

### Required Decorators

- `@Roles(...)` for coarse role checks.
- `@RequirePermissions(...)` for permission checks.
- `@ProjectRoles(...)` for project membership role checks.
- `@Public()` for auth endpoints if a global auth guard is introduced.

## Missing Permission Checks

### Reporting

- Executive summary can be viewed by any authenticated user.
- Portfolio summary can be viewed by any authenticated user.
- Project list returns all projects to any authenticated user.
- RAID list returns all RAID records to any authenticated user.
- Risks list returns all risks to any authenticated user.

### Project Workspace

- Any authenticated user can retrieve any project details by id.
- Any authenticated user can retrieve project members for any project.
- Any authenticated user can retrieve project risks, issues, assumptions, dependencies, and tasks for any project.
- Any authenticated user can add, update, or remove project members.
- Any authenticated user can create, update, or delete project-scoped tasks.

### Tasks

- `GET /tasks/my` and `GET /tasks/my/summary` are correctly self-scoped by authenticated user id.
- General task endpoints are not caller-scoped.
- Direct task updates and deletes do not verify assignee, project membership, project ownership, or role.

### RAID

- RAID creation does not verify that the caller can access or mutate the target project.
- RAID listing is global.
- Risk update/delete does not verify project access, ownership, or elevated role.
- Assumptions, dependencies, and issues do not have explicit standalone guarded mutation endpoints, but they can be created through `/raid`.

## Security Gaps

### High Severity

- Portfolio and Executive dashboards expose portfolio-wide operational data to every authenticated user.
- Project Workspace exposes project details, members, tasks, risks, issues, assumptions, and dependencies to every authenticated user who knows a project id.
- Project membership management can be performed by any authenticated user.
- Project task management can be performed by any authenticated user.
- Global task, RAID, and risk list endpoints expose cross-project data.

### Medium Severity

- User and role administration routes are protected only by JWT, not admin authorization.
- JWT payload contains `roleId`, but role permissions are not loaded or enforced.
- There is no active-user status check after JWT validation.
- Frontend navigation advertises reporting screens to all signed-in users.
- No authorization tests cover forbidden access, cross-project access, or reporting access.

### Low Severity

- Frontend token-presence checks may create misleading affordances by disabling some actions but not reflecting actual permissions.
- Permission entities exist but are currently unused by guards, which can create false confidence in RBAC readiness.

## Frontend Authorization Recommendations

- Add authenticated user profile and permissions endpoint, for example `GET /auth/me`.
- Store effective permissions in frontend auth state.
- Filter navigation items by permission:
  - Executive: `executive:summary:read`
  - Portfolio: `portfolio:summary:read`
  - Projects: `projects:read:assigned` or `projects:read:all`
  - My Tasks: `dashboard:read:self`
  - Risks/Issues/RAID: `raid:read:assigned` or `raid:read:all`
  - Users: `users:read`
- Hide or disable actions based on permission:
  - Create project
  - Add/remove member
  - Create/update/delete task
  - Create/update/delete RAID item
  - Create user/role
- Add forbidden states for screens when the backend returns `403`.
- Do not rely on frontend hiding for enforcement.

## Priority Remediation List

### P0 Before v1.0.1 Release

1. Add `RolesGuard` or `PermissionsGuard` and enforce it on Executive and Portfolio endpoints.
2. Add project access policy checks for `GET /projects/:id` and project-scoped risks, issues, assumptions, dependencies, tasks, and members.
3. Restrict project member add/update/delete to project owner/admin/PMO.
4. Restrict project task create/update/delete to project owner, project manager, delivery lead, or assignee where appropriate.
5. Restrict global `GET /tasks`, `GET /raid`, and `GET /risks` to elevated roles or scope results to assigned projects.
6. Add forbidden-access tests for cross-project access and reporting endpoints.

### P1 Hardening

1. Add active-user status checks after JWT validation.
2. Add an effective-permissions endpoint for frontend navigation and action visibility.
3. Restrict user and role administration to Admin.
4. Add resource owner checks for risk, issue, assumption, dependency, task, and notification mutations.
5. Add API contract documentation for `401` and `403` responses.
6. Add audit logging for denied and successful privileged actions.

### P2 Refinement

1. Add field-level update policies for tasks and RAID records.
2. Add row-level database query scoping for project-assigned data access.
3. Add permission-aware frontend route guards and consistent forbidden states.
4. Add permission seed data and tests verifying role-permission assignments.
5. Add portfolio/program-level scoping once Program Management is introduced.

## Suggested v1.0.1 Acceptance Criteria

- Executive and Portfolio summaries return `403` for users without reporting permissions.
- Project Workspace returns `403` for authenticated users who are neither project members, project owners, nor portfolio viewers.
- Project membership mutations return `403` for ordinary contributors.
- Project task mutations enforce project role and assignee rules.
- Global list endpoints are either removed from general access or filtered by the caller's accessible projects.
- Frontend navigation hides Executive and Portfolio for users without reporting permissions.
- Backend tests cover at least one allowed and one denied case for each high-risk endpoint group.
- Documentation lists the enforced roles and permissions.

## Final Assessment

Current authorization readiness: not ready for v1.0.1 hardening release.

The platform has authentication coverage on the reviewed controllers, but it does not yet have enforceable role-based, permission-based, or project-scoped authorization. v1.0.1 should focus on backend enforcement first, then permission-aware frontend navigation and action visibility.
