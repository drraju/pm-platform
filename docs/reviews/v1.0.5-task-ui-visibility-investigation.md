# v1.0.5 Task UI Visibility Investigation

Date: 2026-06-12
Branch baseline: `release/v1.0-stable`
Scope: Audit only. No application code or business logic changes were made for this investigation.

## Executive Summary

The task CRUD UI is present in the current frontend source, but it is conditionally rendered. The issue is not missing implementation in the checked-out source. The most likely causes for controls not appearing are:

1. The logged-in user does not satisfy the frontend role or project membership checks.
2. The running Docker frontend container was built before the current source changes and has not been rebuilt.
3. The user is looking at `/tasks` expecting full CRUD, but full create/edit/delete controls are only implemented in the Project Workspace Tasks tab.

The frontend does not ask the backend for effective permissions. It infers visibility from the decoded JWT user, the `/users` response, and the project membership returned by `/projects/:id`.

## Visibility Conditions

The Project Workspace page computes visibility from the stored session user, users list, and project members:

- Session comes from `getStoredSessionUser()`: `frontend/lib/api/client.ts:212`.
- `getStoredSessionUser()` decodes `pm_platform_access_token` from browser local storage and requires `sub`, `email`, and `roleId`: `frontend/lib/api/client.ts:235`.
- Current user is matched from `/users` by `sessionUser.userId` or `sessionUser.email`: `frontend/app/(app)/projects/[id]/page.tsx:299`.
- Current project membership is matched from `project.members` by `sessionUser.userId`: `frontend/app/(app)/projects/[id]/page.tsx:303`.

Effective frontend checks:

```ts
const roleName = currentUser?.role?.name ?? "";
const hasGlobalTaskManagement =
  roleName === "Program Manager" || roleName === "Project Manager";
const hasProjectManagement =
  currentMembership?.role === "owner" || currentMembership?.role === "manager";
const isExecutive = roleName === "Executive";
const canManageTasks =
  !isExecutive && (hasGlobalTaskManagement || hasProjectManagement);
const canManageTeam = canManageTasks;
const canUpdateAssignedTasks = !isExecutive && Boolean(currentMembership);
```

Evidence: `frontend/app/(app)/projects/[id]/page.tsx:493`.

## Backend and Frontend Permission Mismatch

Backend v1.0.5 permissions exist, and project/task services enforce manager-level behavior using backend-side checks:

- Backend manager role names are `Program Manager` and `Project Manager`: `backend/src/modules/projects/projects.service.ts:37`, `backend/src/modules/tasks/tasks.service.ts:25`.
- Project `owner` and `manager` memberships can manage project tasks/team: `backend/src/modules/projects/projects.service.ts:38`, `backend/src/modules/projects/projects.service.ts:356`.
- Team members can update only `assigneeId`, `remarks`, `percentComplete`, and `status`: `backend/src/modules/projects/projects.service.ts:39`, `backend/src/modules/projects/projects.service.ts:396`.
- Task assignee must be a project member: `backend/src/modules/projects/projects.service.ts:337`, `backend/src/modules/tasks/tasks.service.ts:210`.

However, the frontend does not check the actual permission keys such as `task.create`, `task.update`, `task.delete`, or `task.reassign`. It uses role names and project membership.

Important mismatch: the v1.0.5 migration grants task/team permissions to `Delivery Lead`, but the frontend global manager role check does not include `Delivery Lead`. Evidence:

- Migration grants permissions to `Program Manager`, `Project Manager`, and `Delivery Lead`: `backend/src/database/migrations/002_v1_0_5_project_teams_task_operations.sql:22`.
- Frontend global task managers are only `Program Manager` and `Project Manager`: `frontend/app/(app)/projects/[id]/page.tsx:501`.

A `Delivery Lead` will only see project task management controls if they are also a project member with role `owner` or `manager`.

## Current Logged-In User Verification

The current logged-in browser user could not be verified from static source files. The application stores the active access token in browser local storage under `pm_platform_access_token`; that state is runtime/browser-specific and is not present in the repository.

To verify the current logged-in user:

1. Open the app in the same browser where controls are missing.
2. Inspect local storage for `pm_platform_access_token`.
3. Decode the JWT payload.
4. Confirm payload contains `sub`, `email`, and `roleId`.
5. Confirm `/users` returns a user matching `sub` or `email` and includes `role.name`.
6. Confirm `/projects/:id` returns `members` and that the member with `userId === sub` has `role` of `owner` or `manager`, unless the user role is exactly `Program Manager` or `Project Manager`.

Expected seeded users include Program Manager, Project Manager, and Delivery Lead test personas. If using a Delivery Lead account, confirm project membership role is `owner` or `manager`; backend permissions alone will not make the frontend buttons visible.

## Docker Build Verification

The Docker build is configured to include current frontend source when the image is rebuilt:

- `frontend/Dockerfile` uses `COPY . .` before `npm run build`: `frontend/Dockerfile:10`.
- The runner image copies `.next` from the builder: `frontend/Dockerfile:18`.
- Compose builds frontend from `./frontend`: `docker-compose.yml:53`.

There is no frontend source volume mount in `docker-compose.yml`. Therefore, an already-running frontend container will continue serving the bundle it was built with. Local source changes will not appear until the frontend image/container is rebuilt and recreated.

Exact deployment verification steps:

1. Rebuild/recreate the frontend service from the repository root: `docker compose build frontend && docker compose up -d frontend`.
2. Hard refresh the browser.
3. Open a project details page at `/projects/:id`.
4. Verify the tab row includes `Tasks` and `Project Team`.
5. Verify manager-level users see `Create Task`, `Edit`, `Reassign`, and `Delete`.

## Root Cause

The source-level root cause of "task CRUD UI is not visible" is conditional visibility, not missing implementation.

Most likely runtime root causes:

1. Logged-in user does not meet frontend manager conditions: role is not exactly `Program Manager` or `Project Manager`, and project membership role is not `owner` or `manager`.
2. Logged-in user is `Executive`, which intentionally hides task/team management controls.
3. Session token is missing, invalid, or cannot be decoded by `getStoredSessionUser()`.
4. `/users` does not return the current user with role information.
5. `/projects/:id` does not return the current user in `members`, or membership role is `contributor` or `viewer`.
6. The running Docker frontend was built from an older source snapshot.
7. User is viewing `/tasks`, where full CRUD is not implemented; only inline personal updates are available.

## Exact Steps Required to Make Controls Appear

For full Project Workspace task CRUD controls:

1. Sign in as a user whose role name is exactly `Program Manager` or `Project Manager`.
2. Or ensure the signed-in user is a member of the target project with project role `owner` or `manager`.
3. Ensure the user is not role `Executive`.
4. Open `/projects/:id`.
5. Select the `Tasks` tab.
6. Rebuild/recreate the frontend Docker container if using Docker and source was changed after the image was built.

For Team Member task controls:

1. Sign in as a non-Executive user.
2. Ensure the user is a project member.
3. Ensure the task is assigned to that same user.
4. In the Project Workspace Tasks tab, the user should see `Reassign` for their assigned rows only.
5. On `/tasks`, assigned tasks should show inline status, percent complete, remarks, reassign, and save controls.

For Project Team management controls:

1. Sign in as a user who can manage tasks by the same conditions above.
2. Open `/projects/:id`.
3. Select `Project Team`.
4. Add member, update role, and remove controls should appear.
