# v1.0.1 Authorization Hardening

Release Date: 2026-06-07

## Overview

This release implements the high-priority authorization findings from the v1.0.1 Authorization Hardening Review.

The platform previously required JWT authentication on the reviewed backend controllers, but most endpoints did not enforce role, permission, project membership, or project ownership checks. This release introduces centralized permission enforcement and project-scoped access checks for reporting, project workspace, tasks, RAID, and risk workflows.

## Changes Implemented

### Backend

- Added centralized authorization infrastructure:
  - `AuthorizationModule`
  - `AuthorizationService`
  - `PermissionsGuard`
  - `ProjectAccessGuard`
  - `@RequirePermissions(...)`
  - `@ProjectAccess(...)`
  - shared `PermissionKey` constants
- Added default permission mapping for current enterprise seed roles:
  - Admin
  - Executive
  - PMO
  - Portfolio Manager
  - Program Manager
  - Project Manager
  - Delivery Lead
  - Technical Lead
  - Engineer
  - QA Engineer
  - Contributor
  - Viewer
- Added `GET /auth/me` to expose the authenticated user's effective role and permissions to the frontend.
- Protected `GET /executive/summary` with `executive:summary:read`.
- Protected `GET /portfolio/summary` with `portfolio:summary:read`.
- Scoped `GET /projects`:
  - Users with `projects:read:all` see all projects.
  - Users with assigned-project access see only owned/member projects.
- Protected Project Workspace APIs with project access checks:
  - `GET /projects/:id`
  - `GET /projects/:id/members`
  - `GET /projects/:id/risks`
  - `GET /projects/:id/issues`
  - `GET /projects/:id/assumptions`
  - `GET /projects/:id/dependencies`
  - `GET /projects/:projectId/tasks`
- Protected project mutations:
  - Project create requires `projects:create`.
  - Project update requires `projects:update` and project-level management access.
  - Project delete requires `projects:delete` and project-level management access.
  - Member add/update/remove requires project member management access.
  - Project task create/update/delete requires task mutation permission and project-level management access.
- Scoped direct task APIs:
  - `GET /tasks` returns only accessible project tasks unless the user has global project read access.
  - `POST /tasks` requires task create permission and project access.
  - `GET /tasks/:id` requires project read access.
  - `PATCH /tasks/:id` requires task update permission and either project management access or task ownership.
  - `DELETE /tasks/:id` requires task delete permission and project management access.
- Scoped RAID and risk APIs:
  - `GET /raid` returns all RAID only for global RAID readers; otherwise returns assigned-project RAID.
  - `POST /raid` requires `raid:create` and project access.
  - `GET /risks` returns all risks only for global RAID readers; otherwise returns assigned-project risks.
  - Risk read/update/delete now enforces project access and RAID mutation permissions.
- Added active-user checks through effective authorization profile loading.

### Frontend

- Added typed `GET /auth/me` API client support.
- Added reusable `useAuthorization(...)` hook.
- Updated application shell navigation to hide unauthorized sections:
  - Executive requires `executive:summary:read`.
  - Portfolio requires `portfolio:summary:read`.
  - Projects requires project read permission.
  - Risks and Issues require RAID read permission.
- Added direct-access authorization handling for:
  - `/executive`
  - `/portfolio`
- Unauthorized reporting pages now display an access denied state and do not call protected reporting APIs.

## Security Improvements

- Portfolio-wide reporting is no longer available to every authenticated user.
- Executive reporting is no longer available to every authenticated user.
- Project workspace APIs now enforce project ownership, membership, or global project-read permission.
- Project member management is limited to users with management permission and project-level authority.
- Project task mutation is limited to users with task permissions and project-level authority.
- Direct task APIs are no longer globally exposed to all authenticated users.
- RAID and risk list APIs are scoped to accessible projects unless the user has global RAID visibility.
- Frontend navigation no longer advertises reporting sections to users without the corresponding permissions.

## Authorization Matrix Updates

| Area | Permission | Applies To |
| --- | --- | --- |
| User dashboard | `dashboard:read:self` | All active users |
| Executive summary | `executive:summary:read` | Executive, PMO, Portfolio Manager, Program Manager, Admin |
| Portfolio summary | `portfolio:summary:read` | Executive, PMO, Portfolio Manager, Program Manager, Admin |
| All projects | `projects:read:all` | Executive, PMO, Portfolio Manager, Program Manager, Admin |
| Assigned projects | `projects:read:assigned` | Project Manager, Delivery Lead, Technical Lead, Engineer, QA Engineer, Contributor, Viewer |
| Project create | `projects:create` | Admin, PMO, Portfolio Manager, Program Manager, Project Manager |
| Project update/delete | `projects:update`, `projects:delete` | Elevated portfolio roles or project managers with project authority |
| Project members | `project-members:read`, `project-members:manage` | Read for assigned users; manage for project owner/manager and elevated roles |
| Project tasks | `project-tasks:*` | Scoped by project authority and task ownership |
| RAID | `raid:*` | Scoped by assigned projects unless global RAID read permission exists |
| Users and roles | `users:*`, `roles:manage` | Modeled but not fully enforced in this release |

## Remaining Authorization Gaps

- User and role administration endpoints still need Admin-only enforcement.
- Notifications should be explicitly self-scoped and permission protected.
- Standalone Issues, Assumptions, and Dependencies mutation endpoints are not yet implemented.
- Field-level task and RAID update permissions are not yet enforced.
- Frontend authorization currently hides major navigation and reporting pages, but all action buttons should eventually be permission-aware.
- Swagger should be expanded with explicit `401` and `403` response documentation across protected endpoints.
- Permission seed data is not persisted to `permissions` and `role_permissions`; default permission mappings currently bridge existing seed roles.
- Audit logging for allowed and denied privileged actions remains outstanding.
