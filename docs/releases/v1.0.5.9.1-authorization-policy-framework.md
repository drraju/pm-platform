# v1.0.5.9.1 Authorization Policy Framework and Project Governance Hardening

## Summary

This release replaces scattered role-name authorization checks with a centralized permission-based policy framework and hardens project governance management across the platform.

The update introduces a shared `AuthorizationPolicyService`, applies explicit project mutation authorization at the service layer, completes core project CRUD in the UI, and adds governance ownership fields to the project model.

## Backend Changes

### Centralized Authorization Policy

Added `AuthorizationPolicyService` with policy methods for:

- `canViewProject`
- `canManageProject`
- `canDeleteProject`
- `canManageTask`
- `canManageRaid`
- `canViewPortfolio`
- `canViewExecutive`

This service now acts as the shared authorization decision point for project, task, RAID, and visibility workflows.

### Removed Embedded Role Checks

Removed direct role-name authorization logic from:

- `PermissionsGuard`
- `ProjectsService`
- `TasksService`
- `RaidService`
- `ProjectVisibilityService`

Authorization decisions are now based on granted permissions, project ownership, project membership, and scoped visibility rules instead of hardcoded role names.

### Project Mutation Hardening

Applied explicit service-level authorization checks to project mutations:

- `POST /projects`
- `PATCH /projects/:id`
- `DELETE /projects/:id`

Project creation, update, and deletion now validate authorization inside `ProjectsService` even if a route is incorrectly exposed later.

### Project Governance Fields

Added governance ownership fields to the `projects` domain model:

- `businessOwner`
- `executiveSponsor`
- `deliveryLead`

The entity, DTOs, migration, seed data, API client types, and UI were updated to support these fields end to end.

## Frontend Changes

Completed core project CRUD support in the projects experience:

- Added edit project flow
- Added delete project flow
- Added confirmation dialog for destructive delete
- Added governance fields to project create/edit forms
- Added edit/delete actions to the projects table when permissions allow

Project overview surfaces now show business owner, executive sponsor, and delivery lead information.

## Remaining Technical Debt

- Authorization still derives effective access from runtime permission checks rather than a formal policy graph or cached access model.
- Project list rendering still enriches rows with per-project detail fetches in the UI, which can become an N+1 pattern as project counts grow.
- Visibility and governance are project-scoped, but stronger tenant or organization boundary modeling is still needed for larger enterprise deployments.
- Permissions are more centralized now, but some workflow-specific business rules still live in services rather than a deeper domain policy layer.

## Outcome

v1.0.5.9.1 establishes a cleaner authorization foundation for upcoming planning and governance work while reducing the risk of inconsistent project access decisions across the platform.
