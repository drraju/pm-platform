# v1.0.4 Bootstrap Super Admin

## Summary

v1.0.4 adds a bootstrap Super Admin account for first-run platform administration. The Super Admin uses the existing authorization framework but bypasses permission and project-access checks centrally.

## Super Admin Architecture

Role:

```text
SUPER_ADMIN
```

Characteristics:

- Full platform access.
- Bypasses `PermissionsGuard` through `AuthorizationService.assertHasAnyPermission`.
- Bypasses project restrictions through `AuthorizationService.assertCanReadProject`, `assertCanManageProjectMembers`, and `assertCanManageProjectTasks`.
- Receives all current permission keys in the auth profile for frontend capability checks.
- Can access all dashboards, all projects, all admin APIs, and future administration features.

The bypass is centralized in `AuthorizationService`; existing permission decorators and guards remain in place for all other roles.

## Seed Behavior

Application startup runs `SuperAdminBootstrapService`.

If missing, it creates:

```text
Role: SUPER_ADMIN
Username: admin
Email: admin@example.com
Status: active
```

If the user already exists by username or email, no duplicate is created. The bootstrap updates the existing user to the `SUPER_ADMIN` role and active status if needed.

Development seed data also includes the same Super Admin identity.

## Default Password Strategy

Default temporary password:

```text
Admin123!
```

The startup password can be overridden with:

```text
SUPER_ADMIN_PASSWORD
```

The startup email can be overridden with:

```text
SUPER_ADMIN_EMAIL
```

## Password Reset Approach

Use the Administration Console:

1. Sign in with username `admin`.
2. Open `/admin/users`.
3. Reset the target user password.
4. Communicate the temporary password through an approved internal channel.

For the bootstrap Super Admin itself, set `SUPER_ADMIN_PASSWORD` before first startup or reset it through the Admin API once authenticated.

## Security Considerations

- Rotate `Admin123!` immediately in non-local environments.
- Set `SUPER_ADMIN_PASSWORD` from a secret manager in deployed environments.
- Restrict Super Admin use to break-glass and platform administration workflows.
- Do not grant `SUPER_ADMIN` to service accounts or external users.
- Audit logging is still a planned administration capability; API surfaces are ready for audit integration.

```sql
ALTER TABLE "users"

CREATE UNIQUE INDEX IF NOT EXISTS "IDX_users_username_unique"
ON "users" ("username")
WHERE "username" IS NOT NULL;
```

```text
roleName = SUPER_ADMIN
```

- `/admin/roles`
- `/admin/permissions`
- `/admin/projects`
