# v1.0.5.1 Authorization Alignment and Governance

Date: 2026-06-12
Branch: `release/v1.0-stable`

## Summary

v1.0.5.1 aligns authorization across database permissions, backend guards, frontend visibility, navigation, and admin governance.

The release preserves existing legacy permission keys and introduces the dot-style v1.0.5 permissions expected by current source code. Frontend task/team visibility now uses effective permissions from `GET /auth/me` instead of hard-coded role names.

## Migration Strategy

Migration file:

- `backend/src/database/migrations/003_v1_0_5_1_authorization_alignment.sql`

Migration behavior:

- Inserts dot-style permissions including `task.create`, `task.update`, `task.delete`, `task.reassign`, `task.comment`, and `project.team.manage`.
- Adds broader governance/navigation permissions such as `user.manage`, `role.manage`, `permission.manage`, `project.read`, `raid.read`, `portfolio.view`, and `executive.view`.
- Preserves legacy permissions such as `project-tasks:create`, `project-tasks:update:any`, and `project-members:manage`.
- Maps existing legacy role grants onto new dot-style permissions where possible.
- Grants full permission coverage to `SUPER_ADMIN` and `Admin`.
- Creates/updates Super Admin user:
  - Email: `admin@example.com`
  - Password: `admin`
  - Role: `SUPER_ADMIN`

## Permission Model

Backend controllers enforce dot-style permission keys through `PermissionsGuard` and `@RequirePermissions`.

Core v1.0.5.1 task/team permissions:

| Permission | Purpose |
| --- | --- |
| `project.team.manage` | Add, remove, and update project members |
| `task.create` | Create project tasks |
| `task.update` | Update task fields |
| `task.delete` | Delete project tasks |
| `task.reassign` | Reassign tasks |
| `task.comment` | Update task remarks |

Governance permissions:

| Permission | Purpose |
| --- | --- |
| `user.manage` | Manage users |
| `role.manage` | Manage roles |
| `permission.manage` | Manage role permission matrix |

Frontend compatibility:

- Frontend permission checks accept dot-style keys.
- Known legacy aliases are also accepted during phased deployments.
- Example: `task.create` is treated as equivalent to legacy `project-tasks:create` for UI visibility.

## Backend Changes

Implemented:

- `GET /auth/me`
  - Returns `{ user, roles, permissions }`.
  - Used by frontend navigation and workspace authorization.
- Permission-aware role responses.
- `GET /users/permissions`
  - Lists permissions for the Admin → Roles matrix.
- `PATCH /users/roles/:id/permissions`
  - Saves role permission assignments from the matrix.
- User and role management routes are protected by permission checks.
- `SUPER_ADMIN` bypass in `PermissionsGuard` as a break-glass safeguard.
- Login accepts existing seeded credentials shorter than registration minimum; registration and user creation still enforce password length rules.

## Frontend Changes

Implemented:

- Login fetches `/auth/me` after authentication and stores effective permission keys.
- App shell navigation reads permissions from `/auth/me` and hides unauthorized routes.
- Project Workspace task actions use permission checks:
  - `task.create`
  - `task.update`
  - `task.delete`
  - `task.reassign`
  - `task.comment`
  - `project.team.manage`
- My Tasks inline updates use permission checks instead of role-name checks.
- Existing Users page now includes an Admin → Roles permission matrix:
  - Permission rows
  - Role columns
  - Checkbox assignment
  - Save matrix action

## Remaining Gaps

- Project/task services still retain project-membership checks for some update paths. That is useful for own-task restrictions but should be reviewed if future permission keys distinguish `task.update.any` from `task.update.own`.
- Existing legacy permission keys remain for backward compatibility. A later release can deprecate them after all deployments return dot-style permissions.
- Screen-level route protection is currently navigation-driven on the frontend. Direct page access still relies on backend API permissions for data and mutation protection.

The temporary Program Manager `user.manage` validation workaround is removed by
`004_v1_0_5_2_authorization_hardening.sql` after introduction of the
assignable-user endpoint.
