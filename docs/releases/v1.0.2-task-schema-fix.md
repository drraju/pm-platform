# v1.0.2 Task Schema Fix

## Root Cause

Timeline Foundation added `tasks.type` to the TypeORM entity model. The application runs with `synchronize: false`, so existing PostgreSQL databases were not automatically altered.

Project list, project detail, dashboard, portfolio, and executive flows load task relations for health and summary calculations. When TypeORM selected the current entity columns from an older `tasks` table, PostgreSQL returned:

```text
QueryFailedError: column Project__Project_tasks.type does not exist
```

The initial schema snapshot had been updated, but no executable migration existed for already-created databases.

During application validation, Project Workspace still returned HTTP 500 after `tasks.type` was repaired. The follow-up check found the existing `Dependency` entity also expected timeline columns that were missing from the live database.

## Migration Details

Added TypeORM migration:

```text
backend/src/database/migrations/1780848000000-AddTaskTypeColumn.ts
```

The migration is idempotent and adds the missing task type column required by the current entity model:

```sql
ALTER TABLE "tasks"
ADD COLUMN IF NOT EXISTS "type" character varying NOT NULL DEFAULT 'task';

UPDATE "tasks"
SET "type" = 'task'
WHERE "type" IS NULL;
```

No new Timeline/Gantt functionality is introduced by this migration.

Added follow-up schema alignment migration for existing dependency entity fields required by Project Workspace:

```text
backend/src/database/migrations/1780848001000-AddDependencyTimelineColumns.ts
```

The migration adds nullable dependency task references and a default dependency type:

```sql
ALTER TABLE "dependencies"
ADD COLUMN IF NOT EXISTS "source_task_id" uuid;

ALTER TABLE "dependencies"
ADD COLUMN IF NOT EXISTS "target_task_id" uuid;

ALTER TABLE "dependencies"
ADD COLUMN IF NOT EXISTS "dependency_type" dependency_type NOT NULL DEFAULT 'finish_to_start';
```

This is a schema consistency repair for fields already present in the current entity model, not new Timeline/Gantt functionality.

## Migration Execution

The migration is registered in the shared TypeORM configuration used by the application, seed framework, and migration runner.

Run after building the backend:

```bash
npm run build
npm run migration:run
```

Normal production startup remains unchanged. Migrations are not executed automatically by `npm run start:prod`.

## Verification Queries

Verify the task table columns:

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'tasks'
ORDER BY ordinal_position;
```

Verify the expected task type column:

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 'tasks'
  AND column_name = 'type';
```

Verify the migration was recorded:

```sql
SELECT *
FROM migrations
ORDER BY timestamp DESC;
```

Verify dependency schema alignment:

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 'dependencies'
  AND column_name IN ('source_task_id', 'target_task_id', 'dependency_type');
```
